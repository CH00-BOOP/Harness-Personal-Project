# 05 · 上下文管理架构设计：用一个对话 case 讲透 T1~T4

> **这篇怎么读**：我们跟着**同一个客户对话**从第 1 轮聊到第 30 轮，看它怎么一步步把上下文窗口撑大，以及每到一个水位、系统用哪一层压缩手段（T1→T2→T3→T4）把它按回预算内。
>
> 每一层都回答同一个问题：**这一层拿到的输入长什么样 → 压缩后变成什么 → 省了多少、代价多大。**
>
> 姊妹篇 [`上下文管理设计方案-对标 ClaudeCode`](../上下文管理设计方案-对标ClaudeCode.md) 讲"为什么"（理念）。本篇讲"具体发生了什么"（跟着一个 case 走一遍）。基本不写代码。

---

## 〇、先立一个心智：窗口是"预算"，不是"容器"

一句话：**上下文窗口不是一个"能装多少装多少"的箱子，而是一个每 token 都要花钱的预算账户。**

塞进去的东西有两重成本：

- **直接成本**：token 花钱、增加延迟。
- **隐性成本（更致命）**：塞的无关信息越多，模型注意力越被稀释，关键信息越被淹没——这叫 **context rot**：窗口还没满，但信噪比已经塌了，模型不升反降。

所以目标不是"尽量多塞有用的"，而是：**在预算内，让模型每一轮恰好看到它需要的，不多不少。** 下面所有压缩动作，都是为这一句服务。

---

## 一、认识主角：一个会越聊越长的对话

### 1.1 我们的 case

一位求职者（叫他**阿哲**）来咨询 IT 课程，边聊边挤牙膏式地暴露自己的情况：

| 轮次 | 客户说了什么 | 这轮暴露的信息 |
|:---:|------|------|
| 第 1 轮 | "我大专，之前做销售，学这个能找到工作吗？" | 学历=大专、背景=销售转行 |
| 第 2 轮 | "我是 22 届的" | 届别=22 届 |
| 第 3 轮 | "主要想去深圳" | 意向城市=深圳 |
| 第 4 轮 | "编程零基础能学会吗" | 基础=零 |
| 第 5~12 轮 | 学多久、有没有同背景学成的、大概拿多少… | 意向逐步升温 |
| 第 13 轮 | "那学费大概多少？" | 进入询价 |
| … | 一路聊到 30 轮 | 历史持续膨胀 |

这个 case 的特点很典型：**信息是零散、多轮才凑齐的**，而且对话会一直变长——正是上下文管理最该治的场景。

### 1.2 每一轮请求，窗口里塞了什么

阿哲每问一句，系统要把下面这些拼成一份"上下文"喂给大模型：

| 组成 | 是什么 | 成本性质 |
|------|------|------|
| **系统提示词（三层）** | 基础流程 + 业务铁律 + 套路总纲 | **常驻税**：每轮都在，越长越贵 |
| **会话历史** | 前面 N 轮聊过的内容 | **膨胀项**：随轮数增长 ← 主战场 |
| **工具结果** | 本轮 recall 的 5 条样本、课程信息、案例 | **临时噪声**：当轮用完就该清 |
| **当前问句** | 阿哲这一句 | 必留 |

我们给窗口划好"预算分区"（用一个演示口径的小窗口，方便看清水位）：

```text
模型总窗口 = 8000 token（演示口径）
├─ 输出预留      1500   ← 一定给回复留够空间，先扣掉
├─ 系统提示词区  ~1200  ← 三层守则，常驻税
├─ 会话画像区    ≤300   ← 外部读回的一句话画像，钉死不压
├─ 活动历史区    弹性    ← 膨胀项，压缩主战场
└─ 工具草稿区    单轮    ← 用完即清
```

**关键规矩**：哪个区超了，就只在哪个区触发对应压缩，互不牵连。下面四层压缩，就是治"工具草稿区"和"活动历史区"这两个会膨胀的区。

---

## 二、T1 微压缩：每轮都跑，免费，纯"删"

**触发**：每一轮无条件先跑。**代价**：0（不调模型）。**动作**：把当轮工具的原始结果用完即弃。

### 输入长什么样

阿哲问第 4 轮"编程零基础能学会吗"，这一轮 Agent Loop 调了 3 个工具，工具草稿区里堆了一大坨原始结果：

```text
【工具草稿区·压缩前】≈ 2100 token
─ recall_playbook 返回 5 条样本（每条 = 客户问题 + 标准答案 + 这么答的原因），约 1400 token
─ course_search 返回完整课程对象：名称/价格/周期/大纲/亮点/关键词/适合人群…，约 500 token
─ student_cases 返回 3 个学员案例的完整档案，约 200 token
```

这些是**给本轮模型决策用的临时草稿**，回复一旦生成完，它们就没用了。

### 压缩后变成什么

```text
【本轮回复生成后】
─ 工具草稿区：清空（这 2100 token 直接丢弃，不进跨轮历史）
─ 进入会话历史的只有两行：
    用户：编程零基础能学会吗
    AI：零基础也能学，我们班里不少同学都是转行来的……（2~3 句）  ≈ 90 token
```

### 省了多少

**2100 token → 90 token**，当轮工具噪声几乎全回收。下一轮开始时，工具草稿区是空的。

> **这一层本项目已经天然做到了**：会话只存"用户消息 + 最终回复"，`recall_playbook`/`course_search` 的中间调用和原始返回从不进跨轮历史。这就是 Claude Code 的 T1——工具原始输出用完即弃。免费又最有效，是最该先做满的一层。

---

## 三、T2 归档：近阈值触发，免费，"搬家"不删

**触发**：活动历史区接近水位（约 60%）。**代价**：0（只是把数据搬到别处）。**动作**：把最老的整段对话，从活动历史区**移到归档区**——不是删，是搬走，不占当前预算但可回溯。

> **关键：T2 靠"规矩"搬家，不靠"读懂"内容。** 它不理解第 1~5 轮讲了啥，只看**机械规则**：谁最老搬谁（比如"活动区只留最近 10 轮"）、或按写入时就打好的重要度标签（`normal` 及以下才搬，`high`/`pinned` 不碰）、或按 token 水位从最老往外搬。这些判断只用到"第几轮、多久以前、什么标签、占多少 token"这类可直接计算的数字，**完全不需要调模型**。它敢这么"无脑按年龄搬"，是因为有两道兜底：①搬≠删，原文在归档区可回溯；②关键事实早已双写进画像（见第七节）。真正负责"记住关键信息"的是画像和 T3，T2 只负责腾地方。

### 输入长什么样

阿哲聊到第 15 轮时，活动历史区里从第 1 轮排到第 14 轮。按"只保留最近若干轮"的规则，最老的第 1~5 轮被判定为可归档（**注意：这是按轮次年龄判定，不是读懂了内容**）：

```text
【活动历史区·搬前】≈ 1600 token
第1轮  大专+销售转行问就业        ┐
第2轮  22届                       │  ← 最老的 5 轮
第3轮  想去深圳                   │     （按年龄规则命中，
第4轮  零基础能学会吗             │      非语义判断）
第5轮  要学多久                   ┘
第6轮 ~ 第14轮  近期对话…（仍活跃）
```

### 压缩后变成什么

```text
【活动历史区·搬后】
第6轮 ~ 第14轮  近期对话…          ← 活动区只剩活跃部分，第1~5轮消失、不再占预算

【归档区（窗口之外·数据库归档表）】
第1~5轮 原文完整保存              ← 可回溯，复盘/需要时能取回
```

### 省了多少 / 为什么不直接删

活动区腾出约 **600 token**，且**一条原文都没丢**——只是挪到了不占预算的地方。之所以要"搬"而不"删"，是因为万一后面 T3 折叠丢了细节，还能从归档区把原文取回来重折。

---

## 四、T3 折叠：~75% 触发，第一次调模型，"一段 → 一句"

**触发**：可用预算用到约 75%。**代价**：中（**要调一次模型**）。**动作**：把一段零散历史**读懂后摘要成一句话**，用这句替换掉窗口里的原文。这是第一次真正调模型——因为"删"和"搬"都做不到"提炼"，产出新文字必须靠模型。

> 这是**最贴合本业务的一层**：阿哲那些挤牙膏式透露的信息，正好可以折叠成一句摘要。
>
> ⚠️ **别把这句"折叠摘要"和第七节的"会话画像"搞混**——它们是两个东西：会话画像是**外部存储里一直在维护的记忆**（从对话第一句就在建），而 T3 折叠只是**窗口内偶尔到水位才做的"腾地方"动作**，它产出的摘要句往往直接引用现成画像即可。详见第八节答疑 Q4。

### 输入长什么样

搬走第 1~5 轮后，活动区里还留着第 6~12 轮共 7 轮零散问答，客户在这里陆续把关键信息说全了：

```text
【活动历史区·折叠前】第6~12轮 ≈ 1500 token
第6轮  用户：像我这种大专的，公司会要吗
       AI：学历不是唯一门槛，我们看重的是项目能力……
第7轮  用户：我之前一直做销售，是不是白干了
       AI：销售经验其实是加分项，转技术岗沟通能力很吃香……
第8轮  用户：深圳这边机会多吗
       AI：深圳 IT 岗位需求很大……
第9轮  用户：像我这种有学成的吗
       AI：有的，深圳好几位同背景学员……
第10轮 用户：他们大概能拿多少
       AI：（结合案例）……
第11轮 用户：我手头不太宽裕，会很贵吗
       AI：（按铁律不直接报价，先确认意向）……
第12轮 用户：那我得先了解下值不值
       AI：理解，我帮您对比一下……
（散落着：大专 / 22届 / 销售转行 / 深圳 / 预算敏感 / 意向中等）
```

### 压缩后变成什么

调一次模型，把这 7 轮**折叠成一句结构化画像**，替换掉原文：

```text
【活动历史区·折叠后】≈ 40 token
[客户画像] 大专 / 22届 / 销售转行 / 意向深圳 / 预算敏感 / 意向强度：中
（第6~12轮原文已折叠为上面这一句；原文仍在归档区可回溯）
```

### 省了多少 / 风险

**1500 token → 40 token**，压缩比约 37:1。后续每一轮，模型只需看这一句画像，而不是重读 7 轮啰嗦问答。

代价：每次折叠调一次模型、有信息损耗风险（比如把"客户特别在意能不能落户深圳"这种细节压没了）。**这正是下一节"外部画像"要兜底的地方。**

---

## 五、T4 全量：~90% 触发，重锤，"整段 → 结构化档案"

**触发**：可用预算用到约 90%，前面几层都削不动了。**代价**：高（调模型，最贵）。**动作**：把整段对话流水**砸成一份结构化会话档案**——模板化、且强制"客户原话逐字保留"。

### 输入长什么样

阿哲一路聊到第 30 轮，即便前面折叠过，新积累的历史 + 折叠句又逼近爆窗。这次要处理的是**几乎整段对话流水**（当前活动区全部内容）。

### 压缩后变成什么

按一份**贴合本业务的档案模板**产出（原话逐字保留，其余结构化）：

```text
【结构化会话档案】
1. 客户原始诉求（逐字）："我大专，之前做销售，学这个能找到工作吗"
2. 客户画像：大专 / 22届 / 销售转行 / 零基础 / 意向深圳 / 预算敏感
3. 当前意向强度：中（多次追问就业与薪资，尚未确认报名）
4. 已给过的佐证：已展示深圳 3 位同背景学员案例（最高 28k）
5. 已触发的关键动作：尚未引导对接班主任；未做任何包就业承诺
6. 待跟进：客户关心性价比，下一步需引导对接班主任一对一谈方案
```

### 为什么最后才用它

它最贵、且压得最狠，所以只在 T1/T2/T3 都不够时才动用。为防止"压走样"，模板强制第 1 条**逐字保留客户原话**——这是把"最不能丢的东西"锁死在结构里。

## 六、四层放在一起看：越贵越晚用

把上面这条 case 的时间线收成一张表，一眼看清"什么水位、上哪层、拿什么当输入、产出什么"：

| 层 | 何时触发 | 调模型？ | 这层的输入 | 压缩后 | 效果 |
|----|------|:---:|------|------|------|
| **T1 微压缩** | 每轮 | 否·免费 | 当轮工具原始结果 2100 token | 只留用户+回复 90 token | 回收当轮噪声 |
| **T2 归档** | ~60% | 否·免费 | 最老第 1~5 轮 1600 token | 搬去归档区，活动区腾 600 | 不删可回溯 |
| **T3 折叠** | ~75% | 是·中 | 第 6~12 轮 1500 token | 一句画像 40 token | 37:1 |
| **T4 全量** | ~90% | 是·高 | 整段对话流水 | 6 段结构化档案 | 重锤兜底 |

> **贯穿原则**：`删（免费）→ 搬（免费）→ 折叠（调模型）→ 砸整段（调模型）`，能用便宜手段绝不用贵的，够了就停——绝不一上来就调模型摘要。

## 七、外部画像：为什么敢把历史压这么狠

T3/T4 压得越狠，越怕丢关键信息。底气来自一份**压缩碰不到的外部笔记**——会话画像，落在数据库里（对标 Claude Code 的 `CLAUDE.md`）。

它**从对话第一句就开始建、每轮增量维护**（所以轮到 T2/T3 压缩时，画像早就在了）。运作只有两个动作，跟压缩完全解耦：

```text
写（落盘）：每轮收尾，从"用户原话 + AI 回复"里抽出关键事实，增量更新画像
读（补漏）：每轮装配时，把这份画像作为"钉死段"读回窗口——压缩永远碰不到它
```

> **注意时序**：画像的"写"发生在**每一轮收尾**，而 T2 归档发生在**很多轮之后**。也就是说——**在 T2 有机会搬走某一轮之前，那一轮的关键事实早就抄进画像了。** 所以 T2 哪怕"无脑按年龄搬"，搬走的也只是"原始流水"，事实还在画像里。（详见第八节答疑 Q3）

用阿哲的 case 说明这份"双份保险"怎么救场：

- **第 11 轮**阿哲说"我手头不太宽裕"，收尾时这条被写进画像的 `预算=敏感`。
- **第 20 轮**做了 T3 折叠，假设模型不小心把"预算敏感"这个细节压丢了。
- **第 21 轮**装配时，画像被原样读回窗口，`预算=敏感` 又回来了——模型不会"失忆"到给一个预算敏感的客户猛推高价方案。

画像里存三类东西（都是"绝不能被压丢"的）：

```text
客户画像：大专 / 22届 / 销售转行 / 意向深圳 / 预算敏感 / 意向中等
关键决策：已展示深圳同背景案例；尚未引导对接班主任；未做任何包就业承诺
客户原话：["我大专，之前做销售，学这个能找到工作吗"]   ← 逐字留档
```

> **它更新很便宜，绝不是"每轮为它单独调一次大模型"**（详见答疑 Q4）：多数字段靠规则抽取（免费），或搭本轮主模型的"顺风车"（顺带多吐几十 token），没新信息的轮次直接跳过。且它永远在压缩范围之外——T3/T4 只动对话流水，画像不动；压完再把画像读回补漏，这就是"敢压狠"的底气。本项目**已有外部存储雏形**（样本库、总纲、指标），补上"会话级画像"就闭环了。

## 八、答疑：几个最容易卡住的问题

下面几个问题，是理解这套机制时最容易卡壳的点，逐个用阿哲的 case 讲清。

### Q1 · T2 和 T3 到底区别在哪？为什么 T2 不调模型、T3 要调？

一句话：**T2 是"按规矩搬家"（原文照搬、不理解内容），T3 是"读懂再提炼"（产出一句新话）。**

| | T2 归档 | T3 折叠 |
|---|------|------|
| 通俗类比 | 微信老消息滚出屏幕 | 给一段聊天写一句"内容摘要" |
| 判断依据 | 第几轮、什么标签（**数字**） | 内容讲了什么（**语义**） |
| 输出 | 原文一字不改，换个地方放 | 一句原文里没有的**新话** |
| 会产生新文字吗 | 不会 | 会 |
| 谁能干 | 几行代码（数据库 move） | 只有模型 |
| 代价 | 免费 | 调一次模型 |

**为什么 T2 不用模型**：搬运不需要理解内容，判断"搬谁"只用到"第几轮、多久以前、什么标签、占多少 token"这些可直接计算的数字。**为什么 T3 必须用模型**：把 7 轮压成一句"客户预算敏感"（客户从没说过这四个字，是从"手头不宽裕""看看值不值"推出来的），这种"读懂 → 归纳 → 重写成新句子"，删和搬永远做不到。

### Q2 · T2 啥都不看，不是瞎搬吗？它到底靠什么标签判断？

**它确实不看内容，但不是瞎搬——它按"时间顺序"搬，而"越老越可能没用"是一个足够好的近似。** 每条消息在**产生的那一刻**就顺手记了一张"身份证"（元数据），全是不用动脑子就能填的字段：

```jsonc
{ "turn": 3, "role": "user", "tokens": 45, "importance": "normal" }
//   第几轮       谁说的        占多少        重要度标签
```

其中 `importance` 这个标签，用**死规则**就能打，不用模型：

| 这条消息是… | 打的标签 | 判断方式（零模型） |
|------|------|------|
| 系统提示词、客户画像 | `pinned`（钉死，永不搬） | 按来源写死 |
| 工具的原始返回 | `ephemeral`（临时，T1 就删） | 按来源写死 |
| 含"价格/承诺/预算"等词的回复 | `high`（重要，尽量别搬） | 关键词匹配 |
| 普通一问一答 | `normal`（普通，可搬） | 默认值 |

**T2 的规矩举例**："活动区只留最近 10 轮；更老、且标签 ≤ normal 的搬去归档。" 阿哲聊到第 15 轮时：

| 轮次 | 内容 | importance | 第 15 轮时 T2 怎么处理 |
|:---:|------|:---:|------|
| 1~5 | 早期问答 | normal | 老于 10 轮 → **搬** |
| 6~14 | 近期问答 | normal | 在最近 10 轮内 → **留** |

翻译成大白话就是：**"序号比（15−10=5）还小、又不是 high/pinned 的，搬走。"** 全程只是**比大小 + 看标签**，一次模型都没调。它压根不知道第 1 轮讲的是"大专销售转行"，只知道"这是第 1 轮，太老了，搬"。

### Q3 · T2 粗暴裁掉后，后续对话要用这些信息，丢了咋办？

**不会丢。核心认知：T2 搬走的是"对话流水"，不是"事实"。事实归画像管。** 关键在**时序——双写发生在搬走之前**：

```text
第3轮  阿哲："想去深圳"
        └─ 本轮收尾就把 [意向城市=深圳] 抄进画像   ← 双写，当轮完成
第4~14轮  画像一直带着"深圳"，每轮读回窗口（pinned，压缩碰不到）
第15轮  T2 把第3轮"原始记录"搬去归档；但 [意向城市=深圳] 在画像里，没动
第20轮  阿哲："深圳落户难吗" → 模型看画像就知道，根本不需要第3轮原文
```

即"记录"没了、"事实"还在。真正依赖旧信息时，三种情况都有兜底：

| 后续依赖的是… | 兜底方式 |
|------|------|
| 关键事实（画像/背景/承诺） | 画像早已双写、每轮读回 → 根本没离开窗口 |
| 画像没覆盖的冷细节（如"表哥也在深圳"） | 原文躺在**归档区**（搬≠删）→ 按需检索取回 |
| 折叠后发现丢了细节 | 从归档区取原文，**重新折叠** |

**唯一会"真丢"的极端链路**：①画像抽取时漏抄 + ②归档区又被物理删除，两个条件同时成立。防法对应两条：让画像抽取尽量覆盖全、归档区只归档不删除（它在窗口外、留着几乎零成本）。

> 一句话：**别把"记忆"寄托在"留着老对话"上——老对话迟早被压掉。真正的记忆是那份每轮读回的画像；老对话退居归档区当"可回溯的原始档案"。** 正因为先有可靠的画像，才敢让 T2/T3/T4 放手压。

### Q4 · 不是 T3 才建画像吗？每轮都更新画像，不是很费 token、很慢？

这里有个命名陷阱：**"画像"其实指两个不同的东西**，搞混就会觉得矛盾。

| | 会话画像（Profile） | T3 折叠产出的"摘要句" |
|---|------|------|
| 是什么 | 外部存储的**结构化笔记**（记忆） | 窗口内替换旧历史的那句摘要 |
| 何时建 | **从第一句就建**，每轮增量更新 | ~75% 水位才偶尔跑 |
| 干嘛用 | 负责"记忆" | 负责"腾地方" |

所以"T2 时没画像"这个担心不成立——画像从第 1 轮就在，T2 在第 15 轮搬东西时它早就有了。T3 那句摘要不是"第一次建画像"，而是**把已有画像落到窗口里替换旧历史**。

至于"每轮更新画像会不会很费 token / 很慢"——**不会，因为更新画像 ≠ 每轮为它单独调一次大模型**：

| 做法 | 成本 | 说明 |
|------|------|------|
| ① 规则抽取 | 0 token、0 延迟 | "大专"→学历、"深圳"→城市，正则就能抽 |
| ② 搭主模型顺风车 | 几乎零 | 本轮为生成回复**本来就要调一次主模型**，让它顺带用结构化输出多吐"本轮新增画像:{城市:深圳}"，只多几十 token 输出，**无新增请求、不加往返延迟** |
| ③ 增量 + 触发式 | 多数轮跳过 | 客户说"嗯""好的""那价格呢"这种没新信息的轮次，检测到无新增就不更新 |

**真正较贵的是偶尔到水位才跑的 T3（重读一大段历史再摘要），不是每轮的画像维护。** 而且因为画像一直被便宜地维护，T3 折叠时那句摘要常常直接引用现成画像，连额外调模型都省了——这正是"能便宜绝不贵"的又一次体现。

## 九、把这一切串起来：某一轮到底怎么装配

上面是"每层单独看"，现在看**完整的一轮**是怎么走完的。以阿哲的**第 21 轮**为例（此时历史已逼近水位），系统在把请求发给模型前，内部走了这么一条流水线：

```text
① 算预算    可用 = 8000 − 1500(输出预留) = 6500
   ↓
② 收原料    系统提示词(三层) + 会话画像(读回) + 活动历史 + 当前问句
   ↓
③ 估账      给每段数 token，按分区汇总 → 发现"活动历史区"到了 ~80%
   ↓
④ 判断      超了！从最便宜的手段开始往下试：
   │  T1 → 工具草稿区本来就空（上一轮已回收），跳过
   │  T2 → 把最老的冷段搬去归档区，还是超
   │  T3 → 折叠第 6~12 轮为一句画像，降到预算内 ✅ 停，不再动更贵的 T4
   ↓
⑤ 装配      按顺序拼成最终消息列表：
            [系统提示词] + [会话画像·钉死] + [折叠后的历史] + [第21轮问句]
   ↓
⑥ 留痕      记录：这轮跑了 T2+T3、省了多少 token、最终多少 token（可解释、可调试）
   ↓
   交还 Agent Loop → 送模型决策
```

两个要点：

- **便宜的先上、够了就停**：走到 T3 已经降到预算内，就绝不再调更贵的 T4。
- **画像永远读回**：即便历史被压得只剩一句，画像里的"预算敏感/意向深圳"每轮都会被重新塞回窗口，防止失忆。

**这条流水线由谁执行？** 就是我们要在 Agent Loop 和大模型之间插的那一层——**上下文管理器（Context Manager, CM）**：

```text
Agent Loop（调度员）
   │  "给我一份装配好的、在预算内的上下文"
   ▼
Context Manager（唯一决定"窗口里放什么"的中枢）
   ├─ 数 token、按分区核算预算
   ├─ 收原料 → 按 T1→T2→T3→T4 顺序压缩 → 拼成最终消息列表
   └─ 读/写外部存储（归档区 · 会话画像）
   ▼
大模型决策 → 执行工具 → 收尾时把关键事实回写画像
```

Loop 不再自己拼上下文，而是**向 CM 要一份现成的**。这样"预算"才有唯一负责人。对照 [04 篇](./04-AgentLoop-一次对话的调度流程.md)，改动只集中在三处：开场"拼上下文"改成"向 CM 要"、工具结果标成临时噪声进草稿区、收尾额外抽取事实更新画像。其余（工具、检索、LLM 抽象）都不用动。

## 十、什么时候该上哪一层（防过度设计）

四层不是一次全开，而是**由真实瓶颈驱动、按水位分档启用**：

| 阶段 | 现状 | 该做什么 |
|------|------|----------|
| **现在**（库小·对话短，单轮 ≤ 6 步） | 主窗口根本撑不爆 | 只保留 **T1**（已天然具备）+ top-k 检索，**T2/T3/T4 用开关关着** |
| **中期**（对话变长） | 多轮历史开始膨胀 | 开 **T3 客户画像折叠** + **画像落盘/读回**（对多轮体验提升最直接） |
| **长期**（规模化） | 超长对话 + 库变大 | 开 **T4 结构化档案** + 套路总纲分域 + 子 Agent 脏活隔离 |

配套的水位/开关都做成配置（`输出预留`、`归档水位≈60%`、`折叠水位≈75%`、`全量水位≈90%`、`ENABLE_T3/T4`…），让治理力度可调。

> **两条安全阀，必须有**：
> - 跑完所有策略仍超预算 → 按重要度从低到高**硬截断**普通历史，但系统提示词/画像这些"钉死段"永不被截；宁可截也不发爆。
> - 摘要模型调用失败 → 降级为"只归档 + 硬截断"，绝不中断对话。
>
> **子 Agent（脏活隔离）现在不做**：当前对话短、库小，上它是过度设计。留好接口，等真出现"某步会拉回海量原始内容"时再上——**知道什么时候不该上，本身就是判断力。**

## 十一、一句话总结

**把"窗口里放什么"的决定权，从散落在 Loop 里的拼接逻辑，收拢到一个有预算意识的中枢（CM）**：它用一条"删→搬→折叠→砸"由免费到昂贵的策略链做压缩，用一份"压缩碰不到的外部画像"做保真兜底——在"让模型记住足够多"与"给未来留足够预算"之间持续权衡。

跟着阿哲这一个 case 看完，你应该能一口气答出：

- **T1**：当轮工具原始结果（2100）→ 只留用户+回复（90），每轮免费删。
- **T2**：最老几轮（1600）→ 搬去归档区（活动区腾 600），免费不删。
- **T3**：零散 7 轮（1500）→ 一句折叠摘要（40，常直接引用现成画像），第一次可能调模型。
- **T4**：整段流水 → 6 段结构化档案（原话逐字留），最贵的兜底重锤。
- **外部画像**：全程双写落盘、每轮读回补漏——正因为有它，前面才敢压得狠。
