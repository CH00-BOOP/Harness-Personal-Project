# 09 · 三代客服架构对比：从「意图路由」到「Agent Loop」

> 前面几篇都在讲这套 Agent Loop 系统「内部怎么转」。本篇换个视角，把它放进**客服架构的演进史**里看——从最传统的「意图识别 + 路由」，到「LLM 版意图路由」，再到你们现在的「Agent Loop」，三代架构用**同一个 case** 贯穿走一遍，看清每一代到底强在哪、死穴在哪、以及哪些环节调了 LLM。
>
> 一句话结论：**三代的分水岭不在「用不用 LLM」，而在「谁决定控制流」。第一代是「分类查表」全程无 LLM；第二代把 LLM 当零件插进固定流水线，控制流仍是开发者画死的；第三代（Agent Loop）把控制权交给 LLM，让它运行时自己决定调什么工具、转几圈、何时作答。前者可控但僵，后者灵活但需边界闸门管控。**

---

## 〇、贯穿全篇的同一个 Case

客户说同一句话，三代架构各跑一遍：

> **「我大专，之前做销售，转行做开发能就业吗？」**

你们的业务套路要求（贯穿判分标准）：
> 涉及就业**绝不乱承诺包就业**，先了解客户背景 → 再用**同背景真实案例**给信心。

记住这条套路，它是拉开三代差距的那把尺子。

---

## 一、第一代：传统「意图识别 + 路由」（全程 0 次生成式 LLM）

### 1.1 调用链路

```text
用户输入
  │
  ▼
① 预处理（分词/纠错/归一化，语音场景还有 ASR）
  │
  ▼
② 意图识别（NLU 分类器）── 把这句话映射到 N 个预定义意图之一
  │   ├─ 置信度 < 阈值 ──▶ 兜底话术 / 多轮澄清 / 转人工
  ▼
③ 槽位/实体抽取（slot filling）── 抽「课程名/城市」等参数
  │
  ▼
④ 对话状态管理（DST/DM）── 维护多轮状态，决定走哪个分支
  │
  ▼
⑤ 路由（router）── 分发到该意图对应的 handler
  │
  ▼
⑥ 取答案：FAQ 条目 / 话术模板 / 固定业务流程
  │
  ▼
⑦ 填槽渲染 → 输出
```

> ⚠️ 关键认知：**经典架构全程不调用生成式 LLM。** 意图分类器是判别式小模型（早期 SVM/FastText，后来微调 BERT——BERT 是语言模型，但这里只做「分类」不做「生成」）；槽位是 NER；DST 是规则；答案是**写死的模板**。整条链路是「查表」，不是「生成」。

### 1.2 Case 走一遍

| 阶段 | 输入 | 输出 | 调 LLM？ |
|---|---|---|---|
| ① 预处理 | `我大专，之前做销售，转行做开发能就业吗？` | 归一化文本 | ❌ 规则 |
| ② 意图识别 | 文本 | `{intent: 就业咨询, confidence: 0.88}` | ❌ 分类小模型 |
| ③ 槽位抽取 | 文本 | `{学历: 大专, 背景: 销售}` | ❌ NER |
| ④ DST | 意图+槽位 | `state = {intent:就业咨询, 可执行}` | ❌ 规则 |
| ⑤ 路由 | state | 分发到`就业咨询handler` | ❌ if-else |
| ⑥ 取答案 | handler | 固定模板：`就业前景很好，我们很多学员都成功转行了！` | ❌ 模板 |
| ⑦ 渲染输出 | 模板 | **「就业前景很好，我们很多学员都成功转行了！」** | ❌ 填槽 |

### 1.3 死穴

- **答案死板**：命中意图只会吐固定模板，做不到「先挖背景 + 拿同背景案例」的套路应答；
- **长尾覆盖差**：没枚举到的问法 = 未知意图，只能兜底/转人工；
- **省略句易翻车**：「Python 那个」这种依赖上下文的话，分类器单独看分不准，全靠 DST 硬编码兜；
- **加能力重**：新增意图要标注→重训→部署（小时~天级），只有算法工程师能改。

## 二、第二代：结合 LLM 的「意图识别 + 路由」

把第一代的②意图分类和⑥取答案换成 LLM，但**骨架没变**：依然是「识别意图 → 路由到预定义 handler → handler 内跑固定流程」。

### 2.1 Case 走一遍

| 阶段 | 输入 | 输出 | 调 LLM？ |
|---|---|---|---|
| ① 预处理 | `我大专，之前做销售，转行做开发能就业吗？` | 归一化文本 | ❌ |
| ② **LLM 意图识别** | 文本 + 意图清单 | `{intent: 就业咨询, entities:{学历:大专, 背景:销售}}` —— 一步做完分类+抽槽，**免标注免重训** | ✅ 分类/抽取 |
| ③ 路由 | `intent=就业咨询` | 分发到**预定义的**`就业咨询handler` | ❌ 查路由表 |
| ④ handler 固定编排 | 意图+槽位 | 按开发者写死的流程：`就业咨询handler = [检索就业FAQ → LLM生成]` | 视配置 |
| ⑤ RAG 检索 | query | 召回「就业相关话术/FAQ」 | ❌ 向量检索 |
| ⑥ **LLM 生成答案** | FAQ + 客户问 | 「转行做开发是可行的，关键看学习投入……我们很多学员转型成功」 | ✅ 生成 |
| ⑦ 输出 | | 上面那段回复 | ❌ |

### 2.2 强在哪、仍差在哪

**强**：答案不再死板（LLM 会结合 FAQ 生成、会变通）；免标注免重训（zero-shot 意图）。

**仍差**：它**只做了 handler 里写死的两步**（检索 FAQ → 生成），**不会主动去调「同背景学员案例」**——因为开发者没在这个 handler 里编排这一步。想让它调案例，就得**改代码**给 handler 加一步。

```text
                ┌── 就业咨询handler → [检索FAQ → 生成]   ← 本 case 走这条
用户 → ②LLM识别意图 ─┼── 询价handler   → [查价格表 → 生成]
                ├── 优惠handler   → [查活动 → 生成]
                └── 低置信 → 兜底/转人工
         ↑ LLM 只负责「选哪条路」和「路尽头生成一句话」，路本身是画死的静态图
```

> 一句话：**LLM 在②和⑥各干了一次活，但整条路线是人预先画死的。**

## 三、第三代：Agent Loop（你们现在的架构）

没有意图表，没有预定义 handler。LLM 看着一堆工具，**每一步自己决定调什么**（04 篇的受控循环）。

### 3.1 Case 走一遍

| 圈 | LLM 决策（运行时自己定） | 引擎动作 | 调 LLM？ |
|---|---|---|---|
| 第 1 圈 | 「按铁律先查套路」→ `recall_playbook("转行就业")` | 执行检索，回填就业套路样本；旁路标记命中知识库 | ✅ 决策 |
| 第 2 圈 | 看到套路写着「就业要用真实案例给信心，且已知客户大专+销售」→ **自己决定**再调 `student_cases(背景=销售转开发)` | 执行检索，回填同背景案例 | ✅ 决策 |
| 第 3 圈 | 「资料够了」→ `final` 生成回复 | 输出，跳出循环 | ✅ 生成 |
| 输出 | 「先别急着下结论，你之前做销售、想转开发——我们正好有位同样销售转型的学员……」（守住不承诺包就业，先挖背景+拿案例给信心） | | |

引擎每圈都实打实调一次 LLM 做决策：

```62:70:ai-customer-service/app/agent/loop.py
            step += 1
            schemas = self._tool_schemas()

            # ① LLM 调用前:记录本步喂给模型的完整上下文(调试"上下文是什么")
            trace.append({"step": step, "type": "llm_call",
                          "messages": copy.deepcopy(messages),
                          "available_tools": [t["name"] for t in schemas]})

            decision = self.llm.chat(messages, schemas)
```

### 3.2 关键差异

「要不要调案例检索」这个决定，是 **LLM 在第 2 圈自己做的**，不是开发者预先编排的。如果客户这句里还夹了「多少钱」，LLM 会**自己多转一圈**去调 `course_search`——**不改一行代码**。

```text
用户 → LLM决策 ─┬─要调工具?→ 执行→回填→(带新资料回到LLM再决策)  ← 循环，步数动态
              └─能答了?→ 生成输出
         ↑ 路线不是画死的，是 LLM 每圈现算出来的
```

## 四、三代总对照

| 维度 | ①传统意图路由 | ②LLM 意图路由 | ③Agent Loop |
|---|---|---|---|
| **控制流谁决定** | 开发者（状态机） | **开发者**（静态路由图+固定 handler） | **LLM 运行时动态决定** |
| **LLM 角色** | 无 | 被调用的**零件**（分类/生成） | 循环的**大脑/调度者** |
| **调 LLM 的环节** | 0 处 | ②意图 + ⑥生成 | **每一圈决策 + 最终生成** |
| **步骤数** | 固定 | 固定（handler 写死） | 动态（1~N 圈，07 篇延迟来源） |
| **答案形态** | 固定模板 | LLM 结合 FAQ 生成 | LLM 按套路+上下文生成 |
| **没编排过的组合** | 兜底/转人工 | 落到最近意图，漏答 | 自由组合工具应对 |
| **要维护意图表吗** | 要 | 仍要（意图冲突仍在） | 不需要 |
| **加新能力** | 标注→重训→部署 | 加意图+写 handler（改代码） | 教样本/加工具即可（01 篇即时生效） |
| **可控/可预测** | 高 | 高 | 低，需边界闸门（04 篇步数/超时） |
| **典型故障** | 路由错、漏答 | 复合意图路由错、handler 没编排到就漏 | 可能「钻牛角尖」多转圈（闸门收） |

## 五、一个好记的比喻

- **①传统意图路由 = 按固定线路跑的公交**：站点写死，不到的地方一律去不了。
- **②LLM 意图路由 = 更聪明的导航按「预设路线」开**：岔路口用更强传感器（LLM）识别走哪条，但**路线图是人提前画死的**，没画的路上不去。
- **③Agent Loop = 司机自己开**：看着实时路况（工具结果）**自己决定走哪、要不要绕路加油**，路线边开边生成。

## 六、一句话回答本篇的核心问题

| 问题 | 回答 |
|------|------|
| **三代的分水岭是什么？** | 不是「用不用 LLM」，而是「谁决定控制流」——开发者画死 vs LLM 运行时自决。 |
| **传统意图路由调 LLM 吗？** | 0 次。全程是分类+抽取+查表+填模板。 |
| **LLM 意图路由和 Agent Loop 差在哪？** | 前者 LLM 是固定流水线上的零件，路线人画死；后者 LLM 掌控制流，路线运行时自生成。 |
| **本 case 里的差距？** | 前两代给不出「同背景案例」（没编排/模板固定）；Agent Loop 自己决定多调一次案例检索，答出套路。 |
| **各自适用场景？** | 高频固定 FAQ 用意图路由（省、快、可控）；长尾/需推理/个性化用 Agent Loop（覆盖广、会变通）——成熟系统常两者混合。 |
